# План работ над API Gateway

## Цель

Подготовить интеграционный MVP API Gateway на Go в два этапа приёмки:

1. Проверить поведение Gateway на контрактных заглушках и каждом доступном сервисе.
2. Выполнить сквозную проверку с реальными сервисами Auth, Core и Game.

Календарных оценок пока нет. Переход к следующей фазе возможен только после
выполнения критериев завершения текущей.

## Границы MVP

Включено:

- публичный HTTP-прокси к Core; поведение сервиса определяется снимком OpenAPI Core;
- точные HTTP-маршруты Auth и Game из предоставленных снимков OpenAPI и
  согласованных [правил прокси](PROXY.md);
- аутентификация по токену доступа на Gateway;
- передача доверенной идентичности пользователя и идентификатора запроса;
- CORS для согласованных источников фронтенда;
- структурированные журналы запросов, тайм-ауты, проверки работоспособности
  и готовности, корректное завершение работы;
- многоэтапная сборка контейнерного образа и последующее интеграционное окружение Docker Compose.

Отложено:

- чат по WebSocket;
- маршрутизация уведомлений;
- интеграция развёртывания с работающим Game Service до предоставления
  поддерживаемой сборки, маршрута проверки работоспособности и процедуры запуска;
- бизнес-авторизация, которая остаётся в целевом сервисе — владельце данных;
- метрики, распределённая трассировка и ограничение частоты запросов,
  если они не станут явными требованиями MVP.

## Фаза 0 — согласовать контракты, влияющие на реализацию

Записывайте ответы в `docs/INTEGRATION.md`. Сохраняйте версии каждого документа
OpenAPI, используемого для реализации.

Уточнение от 2026-09-29 заменяет прежнее решение о публичном gRPC.
Согласованный поток: фронтенд → HTTP-прокси Gateway → HTTP Core, без отдельных
DTO Core или схемы ошибок Gateway. Правила маршрутизации, доверенных заголовков,
JWT, CORS и собственных ошибок Gateway фиксируются в [описании границы прокси](PROXY.md).
Снимок OpenAPI Core в репозитории остаётся источником операций и ответов Core.
Исправление маршрутизации Core от 2026-10-01 добавляет `/api/v1` и в публичные
пути, и в пути целевого сервиса. В снимке Core этого префикса всё ещё нет;
подтвердите поддерживаемую сборку Core и исправьте её OpenAPI, прежде чем
заявлять о соответствии.

Снимки Auth и Game теперь содержат списки маршрутов. Перед эксплуатацией
проверьте записанное поведение JWT/Redis и прокси Auth/Game на поддерживаемых
работающих сборках, получите тестовые данные и URL проверок работоспособности,
а также поручите владельцу Auth исправить сведения о `/api/v1`, Bearer,
заголовке идентичности и cookie в его OpenAPI.

Критерий завершения: каждый обязательный пункт подтверждён ответственным
владельцем сервиса или явно помечен как временное допущение только для тестов.

## Фаза 1 — запускаемая основа Gateway

- Создать модуль Go и разделить конфигурацию, сборку HTTP-сервера,
  аутентификацию, проксирование и наблюдаемость.
- При запуске разобрать и проверить адрес прослушивания, URL целевых сервисов,
  настройки JWT, источники CORS и тайм-ауты. При неверной обязательной
  конфигурации сразу завершать запуск с ошибкой.
- Добавить `/healthz`, `/readyz`, корректное завершение работы и ограниченные
  тайм-ауты сервера.
- Подготовить многоэтапный Dockerfile с пользователем без прав root в рабочем
  контейнере. Сравнить размер образа с существующим ориентиром 20–30 МБ.

Критерий завершения: бинарный файл запускается с проверенной конфигурацией,
проверки работоспособности работают, завершение корректное, контейнер работает
под пользователем без прав root.

## Фаза 2 — HTTP-прокси Core

- Направлять `/api/v1/requests`, вложенные пути `/api/v1/requests/` и
  `/api/v1/sports` в HTTP Core с тем же путём без преобразования DTO отдельных
  операций. Не публиковать старые пути без префикса.
- Сохранять метод, путь, строку запроса и тело запроса, а также статус, тело и
  сквозные заголовки ответа Core. Бизнес-валидация и формат ответа принадлежат Core.
- Требовать проверенный JWT доступа для всех маршрутов Core. Заменять клиентские
  заголовки идентичности и идентификатора запроса перед вызовом целевого сервиса.
- Удалить публичный слушатель gRPC, схему protobuf и сгенерированный код, адаптер
  gRPC, устаревшие зависимости, тесты и документацию, относящиеся только к gRPC.
- Проверить публичный HTTP-маршрут на заглушке Core, включая аутентификацию,
  поддельные заголовки, передачу ответов, недоступность сервиса и отмену запроса.

Критерий завершения: Gateway предоставляет доступ к Core только по HTTP;
заглушка видит исходный HTTP-запрос с доверенными заголовками Gateway, а клиент
получает HTTP-ответ Core, кроме заголовков, которыми управляет Gateway.
См. [правила прокси](PROXY.md).

## Фаза 3 — аутентификация и доступ из браузера

- Перенести существующую проверку токена доступа из перехватчика gRPC в HTTP
  middleware; сохранить согласованные алгоритм, правила полей JWT и Redis.
- Аутентифицировать каждый запрос к Core, включая GET. Не проверять JWT для
  работоспособности, готовности и CORS preflight.
- Разрешать точные источники фронтенда и HTTP/HTTPS localhost для CORS Auth, Core
  и Game. Разрешить `Authorization` и обрабатывать preflight без JWT; выдавать
  `Access-Control-Allow-Credentials: true` только для разрешённых источников
  в preflight, обычных ответах и ошибках известных API-маршрутов.
- Передавать cookie обновления Auth и `Set-Cookie` через Gateway; поддерживать
  браузерные запросы с credentials между разрешённым источником фронтенда и Gateway.
  За атрибуты cookie и поведение CSRF отвечает Auth; их ещё нужно проверить при работе.
- Оставить проверки прав предметной области в сервисе — владельце соответствующего объекта.

Критерий завершения: тесты покрывают ошибки токенов, публичные маршруты,
поддельные заголовки идентичности, preflight и разрешённые и запрещённые источники.

## Фаза 4 — сопоставление запросов и устойчивость

- Генерировать новый UUID `X-Request-Id`, заменять значение клиента и передавать
  его целевому сервису и клиенту, сохраняя даже при собственном значении в ответе сервиса.
- Возвращать сгенерированный ID запроса в заголовке HTTP-ответа и передавать его
  в Core как `X-Request-Id`.
- Записывать структурированные журналы с ID запроса, HTTP-методом и путём,
  статусом, длительностью и целевым сервисом. Исключить токены, cookie и тела.
- Ограничить ожидание соединения и ответа целевого сервиса, сохранять отмену клиентом.
- Использовать HTTP-статусы для собственных ошибок аутентификации, маршрутизации
  и транспорта Gateway без введения схемы тела ответа Gateway.

Критерий завершения: тесты отличают ошибки Gateway от ответов сервисов,
журналы позволяют сопоставлять вызовы через границу заглушки и не содержат секретов.

## Фаза 5 — первый этап приёмки

- Поддерживать контрактные заглушки на основе снимков OpenAPI Core, Auth и Game.
- Запускать компонентные тесты всех объявленных операций Auth/Game,
  маршрутизации, аутентификации, заголовков, cookie, CORS, ошибок, тайм-аутов,
  работоспособности и завершения работы.
- Запускать доступные Auth, Core и Game по поддерживаемым процедурам после
  предоставления сборок и URL проверок работоспособности.
- Записывать и устранять каждое расхождение OpenAPI с наблюдаемым поведением.

Критерий завершения: набор тестов заглушек и проверенные сценарии с каждым
доступным реальным сервисом проходят. Это ещё не полное завершение MVP.

## Фаза 6 — Compose и полный интеграционный MVP

- Добавить Auth, Core, Game, Gateway и необходимую инфраструктуру в Docker
  Compose после публикации командами поддерживаемых образов и проверок работоспособности.
- Проверить реализованный прокси Game на поддерживаемой сборке Game и её
  версионированном контракте.
- Выполнить сквозные сценарии Auth, Core, обновления токенов, недоступности
  целевого сервиса и Game.
- Опубликовать руководство по конфигурации, запуску, готовности, тестам и известным ограничениям.

Критерий завершения: все три реальных сервиса проходят согласованные сквозные
сценарии в воспроизводимом окружении Compose.

## Рекомендуемые следующие шаги

HTTP-прокси Core, Auth и Game, middleware JWT, ID запроса и CORS, удаление gRPC,
конфигурация, файлы сборки контейнера и компонентные HTTP-тесты присутствуют
в дереве исходников. Тесты на заглушках не доказывают совместимость с работающими сервисами.

1. Получить поддерживаемые сборки Auth, Core и Game, их URL проверок
   работоспособности и исправленный OpenAPI Auth; проверить Gateway на них
   и зафиксировать расхождения.
2. Подтвердить развёртывание фронтенда с тем же источником, поведение cookie
   обновления и CSRF Auth, точные источники фронтенда. Оставить чат за пределами MVP.
3. Перед выпуском настроить публичный HTTPS и защитить Core от прямого
   недоверенного доступа; механизмы развёртывания ещё не выбраны.

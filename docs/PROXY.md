## Маршрутизация

Gateway принимает объявленные пары HTTP-метода и пути под `/api/v1` для Auth,
Profile, Request/Core, Game и HTTP Chat. Неизвестный путь возвращает 404, неверный
метод возвращает 405 с `Allow`. Подстановка пути соответствует одному непустому
сегменту, исключает закодированную косую черту и сегменты `.` и `..`.

| Операция | Поведение |
|---|---|
| `GET/PUT /api/v1/user` | Profile |
| `POST/DELETE /api/v1/user` | Auth |
| `GET /api/v1/user/me` | Profile, тот же путь, заголовок `userId` из `sub` |
| `GET /api/v1/players` и `/api/v1/players/` | Game, путь `/api/v1/players/{sub}` без redirect |
| `GET /api/v1/ban/{email}` | Auth, email в пути, обязательного тела нет |
| `POST /api/v1/results` | Game, query-параметр `dto` сохраняется |
| `GET /api/v1/report/all` | Точный маршрут Chat, до шаблона `/report/{userId}` |

Старые переименованные Auth-маршруты и отсутствующие в новом снимке операции Core
удалены. Gateway не добавляет userId к путям Auth. Сервисный `/health` не публикуется.
Пути, экранирование, query и тела сохраняются, кроме двух псевдонимов players.
Целевые ID в телах и путях не заменяются идентичностью вызывающего пользователя.

Прокси сохраняет статус, тело и сквозные заголовки ответа. Заголовки отдельных
соединений исключаются. Gateway управляет `X-Request-Id` и CORS и не позволяет
сервису заменить их. Автоматические повторы запросов отключены. Транспортные
ошибки дают 502, тайм-аут целевого сервиса даёт 504.

## JWT и списки Redis

Публичные операции Auth:

- `POST /api/v1/user`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/refresh`
- `POST /api/v1/verification/send-password-reset-code`
- `POST /api/v1/verification/password-reset`

Без `Authorization` они доступны анонимно. При наличии заголовка требуется один
`Bearer <access JWT>`, и Gateway выполняет обычные проверки. Пустой, повторный
или неверный заголовок возвращает 401. Остальные бизнес-операции требуют JWT.
Health, readiness, документация и CORS preflight обходят проверку JWT.

JWT проверяется по HS512 с UTF-8 байтами `JWT_SECRET`. Обязательны UUID в `sub`
и `jti`, `type=ACCESS`, `iat` и `exp`. Будущий `iat` и истёкший `exp` отклоняются
без допуска расхождения часов. Неверный JWT не вызывает обращения к Redis.

Для действительного JWT выполняются отдельные `EXISTS` в общем Redis:

| Ключ | Результат при наличии |
|---|---|
| `jwt:denylist:<jti>` | 401 |
| `user:banlist:<sub>` | 403 |

Наличие ключа достаточно. Значение и TTL не интерпретируются, Gateway не пишет
ключи и не кеширует результаты. При наличии обоих ключей возвращается 401.
Недоступность соединения и тайм-аут допускают запрос. Командные и прочие
неклассифицированные ошибки дают 503. Известный отзыв или бан имеет приоритет
над ошибкой другой проверки. Отмена клиентского запроса прекращает обработку.

## Доверенные заголовки и роль

Клиентские `userId`, `X-User-Id` и `X-User-Role` удаляются. Проверенный `sub`
передаётся как `X-User-Id`, для Profile `GET /user/me` используется `userId`.
Gateway генерирует новый UUID `X-Request-Id` и передаёт его сервису и клиенту.

Для операций, требующих `X-User-Role`, используется строковый claim `role`.
Допустимы `ADMIN`, `MODERATOR`, `USER`. Отсутствующая или некорректная роль
даёт 403 только на таких операциях. Роль передаётся для изменения роли,
создания и снятия бана Auth, чтения и закрытия отчётов Chat. Конкретные права
ролей проверяет сервис. На остальных операциях неправильный role не делает
JWT недействительным и не передаётся как доверенная роль.

Auth получает проверенный Bearer и cookie. Profile, Core, Game и Chat получают
доверенные заголовки без Bearer и cookie. Ответные `Set-Cookie` Auth сохраняются.

## CORS и готовность

Разрешаются точные источники из `GATEWAY_CORS_ORIGINS` и HTTP/HTTPS localhost
с допустимым портом. Разрешённым источникам возвращается
`Access-Control-Allow-Credentials: true`, включая ошибки известных API-маршрутов.
Preflight обрабатывается без JWT, разрешает `Authorization` и `Content-Type`.
Числовые loopback-адреса и поддомены localhost автоматически не разрешаются.

`/healthz` проверяет процесс. `/readyz` проверяет Redis и HTTP 200 от явных health
URL всех пяти сервисов с общим deadline. Redirect health не выполняется.
Gateway запускается при недоступном Redis, но readiness в этом случае даёт 503.

## Журналирование запросов

`http_request_completed` содержит ID запроса, HTTP-метод, шаблон маршрута,
целевой сервис, статусы, длительность, объём ответа и проверенный `user_id`.
Общий `/user` журналируется с учётом метода, поэтому GET и POST указывают
разные целевые сервисы.

`denylist_result` и `banlist_result` независимо принимают `not_checked`, `clear`,
`denied`, `unavailable` или `error`. Сохранённое значение
`auth_result=allowed_without_denylist` обозначает разрешение при недоступной
проверке Redis. Конкретная проверка видна в двух отдельных полях.
Недоступная проверка записывается с WARN, ошибка проверки с ERROR.
Токены, cookie, тела, исходные пути и query в журнал не попадают.
